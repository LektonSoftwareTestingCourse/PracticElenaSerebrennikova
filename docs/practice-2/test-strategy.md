# Тестовая стратегия

Стратегия описывает подход к тестированию СМП на уровне проекта: почему тестирование организовано именно так и почему часть проверок осознанно исключена из области тестирования. Даты и ресурсы задаёт тестовый план.

## 1. Цель тестирования

Цель тестирования СМП - подтвердить, что процессинговая цепочка «Terminal/Merchant Simulator -> Gateway -> Switch -> Authorization -> Card Management -> Transaction Logger -> Web Dashboard» работает как единое целое, а решение об авторизации принимается корректно: валидные операции одобряются (`responseCode = "00"`), невалидные - отклоняются с правильной причиной (`14`, `54`, `61`, `51`, `05` и др.). При этом доступный баланс и счётчики лимитов меняются согласованно, идентификаторы (`RRN`, `authCode`) корректны и уникальны, а каждая транзакция попадает в лог ровно один раз.

Качество считается подтверждённым, когда для ядра (Authorization, Card-Management) проверено поведение на классах эквивалентности и граничных значениях, для системы в целом пройдены дымовой и критический сценарии, и отсутствуют открытые дефекты критического и высокого уровней.

## 2. Подход к приоритизации (риск-ориентированный)

Объём проверок распределяется по риску, а не поровну между сервисами. Наивысший приоритет - у бизнес-логики, от которой зависит судьба денег и корректность решения: Authorization (порядок проверок, границы лимитов и баланса, полный набор decline-кодов) и Card-Management (алгоритм Луна, генерация PAN, резервирование). Только для этих двух сервисов строится глубокая модель тест-дизайна - классы эквивалентности, граничные значения и попарный набор.

Средний приоритет - у интеграционного стыка «Gateway -> Switch -> Authorization -> Card-Management -> RabbitMQ -> Logger»: ошибки проявляются не в отдельном сервисе, а в связке (маршрутизация, таймауты, идемпотентность, publisher confirms, DLQ). Низкий приоритет - у периферии (симуляторы, Web Dashboard, Notification Service, Bin Lookup): её поведение проще, отказ заметен и не искажает денежные данные, поэтому для периферии достаточно чек-листов дымового тестирования и критического пути.

Отдельный риск - неатомарность пары «проверить баланс -> зарезервировать» (race condition между `GET /api/cards/{pan}` и `POST /api/cards/{pan}/reserve`, см. ТЗ Authorization). Он покрывается нагрузочной проверкой, а не функциональными тест-кейсами.

Подходы к организации (ISTQB) комбинируются: аналитический (проверки выводятся из анализа ТЗ) и риск-ориентированный (приоритет по вероятности и последствиям дефектов) - для ядра; модельный - через модель PICT; чек-листный - для периферии; эвристический - для исследовательских сессий.

## 3. Уровни проверок и их обоснование

| Уровень | Что проверяется | Инструменты | Обоснование |
|---|---|---|---|
| **Unit** | Алгоритм авторизации (порядок и границы проверок), алгоритм Луна, генерация PAN, RRN, `expiryDate` MMYY | JUnit 5 + Mockito | Быстрая и дешёвая локализация дефекта в бизнес-правиле; ветвления и границы удобно покрывать параметризованными тестами |
| **API / интеграционный** | Контракты REST-эндпоинтов сервисов, коды ответов, негативные сценарии, работа с контейнеризованной PostgreSQL | JUnit 5 + RestAssured / Testcontainers | Проверяет стык «код ↔ контракт ↔ БД», где unit-тесты бессильны |
| **Компонентный (асинхронный)** | Публикация/потребление RabbitMQ, outbox-паттерн, retry, DLQ, publisher confirms | Testcontainers (RabbitMQ) | Гарантирует, что ни одна транзакция не теряется и лог не дублируется |
| **E2E** | Сквозные бизнес-сценарии: покупка, возврат (reversal), decline-кейсы | E2E-набор через Gateway + синтетические данные | Единственный уровень, проверяющий всю цепочку сервисов сразу |
| **Нагрузочный** | 500+ транзакций, race conditions при резервировании, метрики p50/p95/p99 | Скрипты нагрузочного прогона | Выявляет неатомарность и деградацию производительности |
| **Ручное исследовательское** | Нестандартные сочетания и «догадки» тестировщика вне модели | Ручные сессии по чек-листам | Дополняет формальные техники там, где модель заведомо неполна |

Настоящий артефакт (модуль 2) наполняет уровни Unit/API (тест-дизайн ядра) и документирует E2E на уровне чек-листа критического пути; реализация автотестов относится к модулям 3–5.

## 4. Область тестирования (scope)

### В области тестирования

- Процессинговая цепочка целиком: приём запроса Gateway, маршрутизация Switch, решение Authorization, резервирование в Card-Management, логирование и отображение в Web Dashboard.
- Бизнес-логика ядра: статусы карт (`ACTIVE`, `INACTIVE`, `BLOCKED`, `EXPIRED`, `DELETED`), срок действия (`expiryDate` MMYY), дневной/месячный лимиты, доступный баланс, алгоритм Луна, генерация тестовых карт.
- Асинхронное взаимодействие: RabbitMQ (транзакции и карточные события), outbox, retry, DLQ.
- Обязательные REST-контракты, помеченные в [`docs/api-spec.md`](../api-spec.md) как `[REQUIRED]`.

### Осознанно вне области тестирования

| Что исключено                                  | Основание                                                                                                                        |
|------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------|
| реальные карточные сети, эмиссия               | СМП - учебная тестовая среда с синтетическими PAN; требования безопасности платёжных систем не применяются                       |
| Нагрузочное тестирование                       | Вне области проектной документации артефакта 2; выполняется отдельным уровнем (модуль 6)                                          |
| Таблицы решений и переходы состояний           | Изучаются на лекции 4 и ограничением задания исключены из артефакта 2                                                            |
| Отчёты о дефектах (баг-репорты)                | Требуют реального прогона; оформляются в модулях 7–8                                                                             |
