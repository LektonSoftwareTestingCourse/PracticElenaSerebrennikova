# Тестовый план

Уровень плана: проектный, состав разделов - по ISO/IEC/IEEE 29119-3.

## 1. Область тестирования и подход

План охватывает всю процессинговую цепочку СМП: Gateway, Switch, Authorization, Card-Management, Transaction Logger, симуляторы, Notification Service и Web Dashboard - а не отдельный сервис.

Подход - чёрный ящик: проверяется поведение сервисов через API. Техники - классы эквивалентности и граничные значения (ядро), дополненные попарным тестированием (модель PICT); приоритизация риск-ориентированная - объём работ следует за риском. Обоснование подхода - в тестовой стратегии.

Стратегия отвечает на вопрос «почему», план - на вопросы «как, кто и когда».

Инструменты: PICT для попарного набора; далее по модулям - JUnit 5 + Mockito, docker compose.

## 2. Критерии входа и выхода

Критерии описывают **весь курс (модули 1–8)**: один и тот же объект тестирования СМП последовательно проходит все уровни пирамиды - от запуска и smoke до финальной тестовой стратегии.

### Критерии входа

Критерии входа проверяются перед каждым этапом курса (модулем):

- Стенд доступен: `docker compose up -d` поднимает 11 сервисов + PostgreSQL + RabbitMQ, `./scripts/smoke-test.sh` завершается `ALL CHECKS PASSED`, все health-check отвечают 200.
- Требования этапа согласованы: актуальные ТЗ и [`docs/api-spec.md`](../api-spec.md) зафиксированы, область модуля согласована с куратором.
- Предыдущий артефакт сдан и принят - модули проходятся последовательно (1 -> 8).
- Тестовые данные подготовлены: карты всех статусов и на границах лимита/баланса/срока (генератор `POST /api/cards/generate`).
- Инструменты этапа установлены: PICT/`allpairspy` (м2), JUnit 5 + Mockito (м3), RestAssured + Testcontainers (м4–6), Allure, GitHub Actions, docker compose.

### Критерии выхода - в измеримых терминах

Критерии выхода - готовность курса (после модуля 8):

- Сданы и приняты **все 8 артефактов** по контрольным точкам (недели 3, 5, 7, 9, 11, 13, 15, 16); по каждому - зелёный CI и пройденная проверка (LLM-рубрика / взаимное рецензирование).
- **0** открытых дефектов критического и высокого уровней.
- Составлена **coverage map**: каждый уровень пирамиды (unit, API, интеграционный, E2E, нагрузочный) закрыт соответствующим артефактом.
- **≥ 95 %** покрытия ключевой бизнес-логики ядра (Authorization, Card-Management); **100 %** decline-кодов и **100 %** пар модели `pict/model.txt` покрыты.
- E2E-набор стабилен (flaky-тесты объяснены или устранены), нагрузочный прогон 500+ транзакций выполнен, метрики собраны.
- Итоговый пайплайн CI/CD зелёный, Allure-отчёт доступен, защита проведена (5–7 слайдов).

## 3. Критерии приостановки и возобновления

### Приостановка

- Инфраструктура не поднимается (сервис в состоянии `unhealthy`, БД или брокер недоступны) и проблема не устраняется в течение 15 минут.
- Найден дефект критического уровня, блокирующий прохождение критического пути (цепочка транзакции не доходит до Logger или теряются данные).
- Тестовые данные испорчены настолько, что дальнейшие проверки нерепрезентативны (например, массово выставлен статус `BLOCKED`).
- Модель PICT/набор попарного тестирования недоступны и не могут быть восстановлены резервным генератором.

### Возобновление

- Причина остановки устранена, `docker compose ps` показывает все контейнеры здоровыми, окружение пересобрано и очищено от грязных данных.
- Блокирующий дефект задокументирован и исключён из области текущего прогона (либо исправлен).
- Тестовые данные перегенерированы, `pict/cases.txt` актуален.

## 4. Ресурсы, расписание, метрики, риски

### Ресурсы

| Ресурс | Состав (весь курс) |
|---|---|
| Команда | Студент (все тесты пишутся заново в течение семестра) + куратор + взаимное рецензирование |
| Окружение | Docker Desktop, VS Code, локальная машина (Windows/Linux/macOS) |
| Инструменты по модулям | PICT/`allpairspy` (м2); JUnit 5 + Mockito (м3); RestAssured + Testcontainers (м4–6); Allure, GitHub Actions (м6, м8); load-smoke (м6); Prometheus/Grafana/Loki - профиль `observability` (м8) |
| Инфраструктура | 11 сервисов СМП + PostgreSQL + RabbitMQ (docker compose), порты 3000, 8080–8088, 8096, 8097, 15672 |
| Данные | Синтетические карты (`POST /api/cards/generate`), сценарии симуляторов, эталонные кейсы ядра |

### Расписание

| Практика | Модуль | Что сдаётся |
|:--------:|---|---|
|    1     | Запуск СМП + smoke | health-check всех сервисов, `smoke-test.sh` |
|    2     | Тест-дизайн | стратегия, план, test-design ядра, чек-листы, модель и набор PICT |
|    3     | Unit-тесты | JUnit 5 тесты бизнес-логики (Gateway, Switch, Authorization, CMS) |
|    4     | API/интеграционные | тесты REST-контрактов и стыков с PostgreSQL/RabbitMQ |
|    5     | E2E | сквозные сценарии покупки / возврата / decline |
|    6     | CI/CD + нагрузочный smoke | пайплайн + Test Summary Report |
|    7     | Отчётность и метрики | Allure, coverage trends, metrics-report |
|    8     | Финальная стратегия | coverage map, ≥ 5 рисков, защита |


### Метрики

- **Покрытие по уровням пирамиды**: доля уровней (unit/API/интеграционный/E2E), закрытых артефактами (цель - 100 %).
- **Покрытие требований и ключевых полей**: ≥ 95 % для ядра (Authorization, Card-Management).
- **Покрытие пар**: 100 % пар модели `pict/model.txt` встречаются в `pict/cases.txt`.
- **Покрытие decline-кодов**: 100 % кодов из [`docs/api-spec.md`](../api-spec.md).
- **Дефекты**: 0 открытых критического и высокого уровней; динамика по модулям.
- **Approval rate / error rate**: по прогонам симуляторов и E2E.
- **Производительность**: p50/p95/p99, throughput (нагрузочный прогон, модуль 6).
- **Стабильность**: доля flaky E2E-тестов (цель - 0 без объяснения).
- **Своевременность**: доля артефактов, сданных в контрольную точку.

### Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Нестабильность окружения (таймауты, race conditions при резервировании) | Высокая | Среднее | Ретраи, детерминированные данные, изоляция прогонов |
| Eventual consistency: лог доходит до Logger с задержкой через RabbitMQ | Высокая | Среднее | Ожидание доставки/опрос вместо мгновенного assert |
| Flaky E2E-тесты | Средняя | Высокое | Идемпотентные данные, повторы, изоляция |
| Обход архитектурного соглашения (прямые запросы в чужую БД) | Низкая | Высокое | Взаимодействие проверяется только через API/очереди |
